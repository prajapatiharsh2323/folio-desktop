# UI-003 — Anchored menus lacked keyboard navigation

- Classification: design inconsistency (fixed for keyboard semantics)
- Severity: P2 Medium
- Confidence: confirmed (RED test → GREEN)
- Area: `src/components/FolioMenu`
- Affected format/platform: all screens using the per-book “…” menu; all platforms
- Commit/build: `ed7a3a1`

## User impact
`FolioMenu` declared `role="menu"` but only handled Escape and outside clicks. Keyboard users could focus the first item but could not move between items or reach disabled-skipped neighbours with the arrow keys.

## Reproduction steps
1. Open a per-book “…” menu; focus starts on the first enabled item.
2. Press ArrowDown/ArrowUp/Home/End.
3. Before the fix, focus stayed on the first item.

## Expected
WAI-ARIA menu semantics: arrows move between enabled items and wrap; Home/End jump to the ends; one tab stop (roving tabindex).

## Actual (before fix)
No arrow/Home/End handling; every item was a tab stop.

## Evidence
- New `tests/folioMenu.test.tsx` failed RED on all three assertions.
- Source: `FolioMenu.tsx` previously only had Escape/outside handlers.

## Root cause
The shared anchored menu implemented the visual and ARIA roles without the corresponding keyboard interaction contract.

## Applied minimal fix
Added an `onKeyDown` handler on the menu root for ArrowDown/Right, ArrowUp/Left, Home and End; maintains `activeIndex`, skips disabled items, wraps, and uses a roving `tabIndex` (0 for active, -1 otherwise). Hover also updates the active item. The menu root is focusable (`tabIndex={-1}`) to satisfy the a11y lint rule.

## Regression test
`tests/folioMenu.test.tsx` (3 tests): first-enabled focus, arrow navigation with disabled skip/wrap, Home/End, roving tab stops.
